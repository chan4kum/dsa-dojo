# Independent teacher's review of this repository

*Reviewed as a DSA instructor would audit a course before putting students in front of it. Method: read every note, run every reference solution and its brute force, compare coverage with public problem lists, and ask of each part: **will a student understand it, remember it, and be able to reproduce it in an interview?***

## Verdict in one paragraph
The spine is strong: concept-first notes, a pattern finder, hint ladders that escalate gently, tests that run locally, and (after this review) a brute-force and an optimised solution for every problem so students see *why* the optimisation exists. The biggest weaknesses found were **coverage** (famous interview problems missing), **retention** (notes explained but did not give images/contrast/teach-back), **pattern recognition practice** (no active-recall tool) and **interview execution** (nothing on communication, being stuck, or the job search). All four were addressed below. Honest limits are listed at the end.

## Gaps found -> what was done
| # | Gap a teacher would flag | Fix in the repo |
|---|---|---|
| 1 | Students only saw the optimal solution, so the *reason* for an idea stayed abstract | Every problem now has a tested **brute force** with its cost next to the **optimised** one. `selftest` requires the brute to be correct (slow is fine); `tools/fuzz_diff.py` checks brute == optimised on random inputs |
| 2 | Missing famous problems (Clone Graph, Alien Dictionary, Word Search II, Serialize Tree, Encode/Decode Strings, LCA of BST, Reverse Linked List II, Coin Change II ...) | Added; Blind-75-style list now fully covered, see `notes/B3-coverage.md` (generated, so it cannot lie) |
| 3 | Concepts explained but not *anchored*: no mental image, no "why does it work", no contrast ("when NOT to use it") | Every topic note ends with **Make it stay - the teacher's anchors**: picture, one-sentence rule, why it works, teach-back prompts, common mistakes, when not to use it, the idea in disguise |
| 4 | Recognising the pattern is the real interview skill, but there was no way to train it | `python dsa.py quiz` shows a problem, makes you commit to a pattern and the costs, then reveals them; misses go into `review` |
| 5 | Nothing on how to run the interview itself (clarify, brute force, test aloud, get unstuck) | `notes/B2-interview-playbook-and-job-search.md`: six-step protocol, stuck protocol, Python pitfalls, behavioural stories, job-search pipeline, AI-engineer track |
| 6 | Matrix problems had no home | New topic `matrix` (rotate, spiral, set zeroes, game of life, sudoku) with a note |
| 7 | Multiple-valid-answer problems (peak, topological order, alien dictionary, reorganize string) can't be tested by equality | Engine got a `check` validator hook and `inplace` hook; tests accept any correct answer |
| 8 | Difficulty ordering inside a topic followed insertion order | Ladders and `list` are now sorted easy -> hard (ids unchanged) |

## What is genuinely good (keep it)
- The *paper-first* method and hand-trace tables generated by running code (never hand-typed, so they cannot be wrong).
- Hint ladders: three nudges, then the pattern name - protects the struggle that builds memory.
- Concept order: each topic uses only earlier ideas.
- Local, dependency-free execution with timeouts, so brute force visibly times out where it should.

## Honest limits (do not hide these from students)
1. **Count**: 808 problems are taught in depth (the target is 1000; 192 still to add). The coverage map shows what is covered; for further practice use the "More:" lists at the end of each note *after* finishing the ladder.
2. **Statements are paraphrases**, not LeetCode's text; always read the official statement via the link before submitting there.
3. **Tests are small and hand-picked** plus random cross-checks; they do not replace a judge's large hidden tests. Complexity claims should be argued by the student, not trusted.
4. **Not covered in depth yet**: segment trees (only Fenwick), Tarjan/Kosaraju SCC, Manacher, advanced geometry, SQL and concurrency questions.
5. **Not tested with real learners.** The first cohort's confusion points should drive the next edit.
6. **Verification has limits.** `check_metadata.py` compares against a third-party mirror of LeetCode's problem list (plus 12 premium entries confirmed by hand on 2026-11-15), not LeetCode itself. `verify_claims.py` proves the claims it lists; it cannot prove that the tutorials contain *no other* wrong sentence. Brute-vs-optimised fuzzing does not cover design problems, and in-place problems (26, 27, 80, 905, 922) are unsupported by the harness. Complexity claims are argued, not measured.
7. **"More:" lists mix solved and unsolved problems.** They were written as transfer-practice lists; some entries are now also full ladder problems in this repo. Treat them as cross-references, not a guaranteed list of unseen problems.
8. **Fast-moving topics** (agent protocols, LLM security lists, interview formats) were checked on 2026-11-15 against secondary sources and will age; re-check before relying on them.
9. **Publishing**: the repository is public at github.com/chan4kum/dsa-dojo; pushes are made from the maintainer's own machine.
10. **Design problems are checked by `selftest` only.** Class-based problems (e.g. Calendar, Text Editor) get hand-written call sequences but no brute-vs-optimised fuzzing, and in-place problems are not supported by the harness. Some brute forces are thin variants of the optimised idea.
11. **Multi-answer problems** (any valid answer accepted) are validated by a `check` function and fuzzed through a normaliser; both are hand-written and only as strong as their rules.
